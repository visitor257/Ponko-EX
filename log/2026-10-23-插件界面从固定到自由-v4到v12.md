# 插件界面：从「宿主定死」到「插件自己排」（SDK v4 → v12）

一天之内从 v4 推到 v12，起因全是插件侧（voxcpm2）在真机上撞出来的。
按撞墙顺序记，重点写**每次为什么改、以及我判断错了什么**。

---

## 一、五个按钮没有否决权

### 现象

插件侧反馈：宿主固定画「加载模型 / 合成 / 播放 / 停止 / 保存」五个按钮，
插件没有否决权。唯一现成的开关是声明 `AUTOLOAD_ENGINE`，它能让「加载模型」消失，
**代价是插件一连接宿主就灌 3.3 GB 权重** —— 完全不能用。

### 原因

`AUTOLOAD_ENGINE` 的语义本来是「要不要**自动加载**」，被我拿去当「要不要**显示**
加载按钮」用了：

```kotlin
val autoLoaded = capabilities.contains(Capability.AUTOLOAD_ENGINE)
if (!autoLoaded) { add(加载引擎按钮) }
```

两件不相干的事绑在同一个开关上，结果两个都用不好。

### 做法

在 manifest 读一行，不动 AIDL、不发 AAR：

```xml
<meta-data android:name="ponko.actions" android:value="reasoning,stop" />
```

`<service>` 和 `<application>` 两处都读（service 优先）。**三态严格区分**：
没写 = 全显示（老插件不受影响）、空串 = 一个都不要、非空 = 过滤。
所以查找用 `?:` 不能用 `?.` —— 空字符串也是有效声明。

> **教训**：需求里出现「只改 app 模块、不碰 AIDL、不发 AAR」这种硬约束时，
> 那是最强的信号 —— 对方已经算过成本。该按那个约束设计，
> 而不是换个约束更松的方案。

## 二、「开始」和「停止」并排，永远有一个是废按钮

### 现象

两个按钮互斥（没在合成时只有开始有意义，合成中只有停止有意义），
并排放着必然有一个灰着白占宽度。

### 做法

叠进同一个格子，靠 `VISIBLE` / `INVISIBLE` 交替。

**必须 `INVISIBLE`，不能 `GONE`** —— `GONE` 会把后面的「保存」往左拽、整行重排，
那就不是"停止顶到原位"，而是"别的按钮挤过来"。叠放在 `FrameLayout` 里还顺带保证
高度不跳（`GONE` 方案连行高都会抖）。

没合并 `play` / `save`：它们可以同时可用，合并会让用户以为一次只能干一件事。

## 三、`HOST_SLOT` 整块搬，表达不了块内顺序

### 现象

插件要「开始按钮在文本下面、进度条在按钮下面」。整块搬做不到 ——
块内顺序写死成：标题 → 按钮行 → 参数区 → 诊断。

### 做法

`HOST_SLOT.value` 支持分段 `actions` / `params` / `diag`，三处各挖一个坑。

两个坑：

1. **三段各自只建一次**（`params` 里是输入框，重建等于清空用户正在打的字）
2. **模式靠预扫描决定**。渲染是流式的，整块坑可能出现在分段坑**之前**，
   那时"已经取过一个"还是 false，会把整块搬走、后面分段就冲突了。
   所以 `render()` 开头扫一遍 `schema.items`

没被挖走的段**仍回顶部** —— 只挖 `actions` 时参数区必须还在，否则用户没地方填文本。

## 四、`items` 一直是纯纵向，两个滑块并排都做不到

### 现象

用户定的方向：「应该做成最大程度自由（除了 theme）」。盘下来和 theme 无关的
大缺口只剩**布局**。

### 做法

加 `ROW_START/END`、`GRID_START/END`、`DIVIDER`、`SPACER`（编号 20–25）。

实现上三个关键决定：

1. **不改 `UiItem` 字段** —— `@Parcelize` 加字段会让所有已发插件必须重编。
   布局参数全走容器自己的 `value`
2. **渲染栈从 2 种 Slot 扩到 4 种，所有插入统一走 `place()`**。
   这是能一次落地的原因：以前每加一种容器都要改一遍所有 `addView` 调用点，
   所以"再加一种布局"看起来永远很贵
3. **GRID 不用 `android.widget.GridLayout`** —— 它按"最宽子项"定列宽
   （按钮文字长短不一就出现参差格子），且 `columnWeight` API 21+ 才稳。
   改成"竖向容器 + 每满 n 个开新行"

两个容易漏的：网格最后一行不满要补透明占位（否则最后那个是唯一 `weight=1`，
被拉满整行）；`place()` 的 `addView(v, params)` 会覆盖控件自带 layoutParams，
`SPACER` 的高度会被冲成 0（加 `keepSize` 开关）。

> 顺手改掉一处自相矛盾：`UiType` 的 KDoc 里原来写着"嵌套布局**刻意不做**"，
> 现在做了，不改就是同一个文件里文档和实现互相打脸。

## 五、宿主写死了六处触发行为

### 现象

用户：「插件 UI 上很多控件你都弄了写死的触发行为，比如按加载按钮会自动跳到
加载按钮所在的位置。这些触发本不应该有，除非是插件自己加的。」

### 原因

每一条当初都有正当理由（多数是修某个具体 bug），但**逐条累积**之后，
效果变成"用户在插件页里被宿主推着走"。

### 做法

| 原来 | 现在 |
|---|---|
| 日志框一渲染就滚到底 | 删。跟随交给 `patch(append)`，且只在"本来就在底部"时 |
| 切标签页就把该页所有日志框滚到底 | 记 scrollY + 是否在底部，切回来放回原位 |
| `patch` 找不到 key 时若只有一个日志框就写进去 | 丢弃 + 日志列出可用 key |
| 送图没带 key 时贴到第一个 `IMAGE` | 只在**恰好一个**图片控件时才贴；多个则丢弃 |
| 日志追加时无条件把整页滚动拉回原位 | 只在"日志框自己在跟到底"时才补（那是防焦点冒泡） |
| `render()` 不保存 scrollY | 见下一节（最终是根因修复） |

判据一句话：**这个动作是插件要的吗？还是宿主顺手加的？**
宿主只该做两类：控件本身语义（拖动、切换、折叠）、宿主自己的状态机
（播放条、按钮可点状态）。其余默认不做。

`onImage` 缺 key 是真协议缺陷（v4 定的签名里没有），v11 追加
`onImageWithKey`，事务码正好在末尾（+12）。

## 六、`render()` 之后页面跳回最顶（连续判断错两次）

### 现象

模型页点「加载模型」→ 页面立刻回到最顶；加载完成、「释放模型」变可点时 → 再回一次。
两次都精确对应一次 `notifySchemaChanged()` → `render()`。

### 第一次判断（错）：以为是恢复时机太早

我在 `render()` 末尾加 `post { scrollTo(0, keepY) }`。`post` 只保证"下一轮消息队列"，
**不保证 measure/layout 跑过**，那时子 View 高度是 0，`scrollTo` 被 clamp 到 0 ——
不但没恢复，反而把位置改坏了。

### 第二次判断（也错）：以为删掉就对了

我删掉整段，注释写「`removeAllViews()` 只 requestLayout 不立即 layout，
帧末 layout 时 `mScrollY` 保持原值 —— **Android 自己就把位置保住了**」。

插件侧读了 AOSP 打回来：

```java
// ScrollView.onLayout 末尾
scrollTo(mScrollX, mScrollY);

// scrollTo 会按当前子 View 高度重新夹
private static int clamp(int n, int my, int child) {
    if (my >= child || n < 0) return 0;   // 内容不高于视口 → 归零
    if (my + n > child) return child - my;
    return n;
}
```

`clamp` **只会变小、不会自己长回来**。所以"Android 自己保住"有个前提：
**内容高度不能在那一帧变矮**。而这一页不满足 —— pager 的高度是在
`OnPreDrawListener`（布局**之后**）设的：

| 时机 | 发生什么 |
|---|---|
| 帧 N layout | 用**新的** ViewPager 自己量的高度（`populate()` 只实例化当前页 ±1） |
| 帧 N pre-draw | 才把高度改成"最高页"，requestLayout |
| 帧 N+1 layout | 高度落定，但 `mScrollY` 已经在帧 N 被夹掉了 |

### 做法（根因）

`ViewPager` 子类，在 `onMeasure` 里遍历所有页取最高值，用 `EXACTLY` 交给 super。
高度在**测量阶段**定好，重建那一帧高度不掉，`ScrollView` 的默认行为就真的能保住位置
—— **不需要任何恢复代码**（没有双层 `afterLayout`，没有 `keepY`）。

同一批修掉的时机问题：pager 定高、日志跟随读 `child.height`、外层位置锁，
全部从 `post` 改成 `OnPreDrawListener`（布局完成、绘制之前，唯一能保证读到最新值）。
**不能用 `OnGlobalLayoutListener`** —— 它的语义是"发生了一次全局布局"，
同一帧可能触发多次，也可能在内容变化前就跑过，拿它判断"尺寸是否最新"会出错。

`afterLayout` 还必须等 attach：`render()` 在 `build()` 里跑，那时页面还没 attach，
`isShown` 必然 false —— 直接判它就退回 `post`，等于没改、原 bug 原样保留。

最后给插件留下显式出口 `notifyScrollTo(key)`（v12）：**宿主不自动滚动，要滚就明说**。

## 一句话版

- **「不做干预」和「放任副作用」是两件事**：前者是不替别人做决定，后者是自己搞坏了还不修。
  第六节第一次和第二次判断，就是把后者当成了前者
- 需求里的硬约束（"不动 AIDL"）是**对方算过成本**的信号，别绕开它设计
- `View.post` ≠ 布局完成。凡是要读 `height` / `getLocationInWindow` 的，一律等 pre-draw
- `ScrollView` 每次 layout 都 clamp `mScrollY`，而且**只往下夹**。内容高度一抖，位置就丢
- `@Parcelize` 加字段 = 所有已发插件必须重编。新能力优先靠新类型 / 新常量，不改字段
- 兼容判据用 `pluginApi >= API_WITH_xxx`，不要用 `== 最新版`
