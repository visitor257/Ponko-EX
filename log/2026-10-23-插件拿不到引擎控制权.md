# 插件拿不到引擎控制权：binder 是 private，状态机永远不动

插件侧报的缺口。**是真的**，而且后果比"界面显示不对"严重得多 —— 同一次合成会跑两遍。

---

## 现象

插件自绘了「加载模型 / 释放模型」按钮（它把宿主那排按钮用 `ponko.actions` 裁掉了），
点下去之后：

1. 宿主功能区那行「引擎」**永远显示"未加载"**
2. 点「开始推理」→ 等 1~2 分钟 → **出来两份结果**
3. 前台服务通知不出现

## 原因

### 表层

`loadEngine` / `closeEngine` / `getStatus` / `isEngineReady` 全都写在
`private val binder = object : IPonkoPlugin.Stub() { … }` 里面。binder 是 private，
**插件一个都拿不到**。

而 `loadEngineBlocking()` 是 `protected` 的，看起来"能调" —— 于是插件唯一的出路
就是直接调它。但它只是**纯阻塞实现**，状态机在别处：

```kotlin
// 插件的写法（唯一可行的写法）
protected fun loadEngineBlocking(...): EngineInfo { /* 真的加载了 */ }
// 但 state 还是 UNLOADED —— 因为那行在 binder 里
```

### 为什么会跑两遍

| 步骤 | 发生什么 |
|---|---|
| 插件按钮 → `loadEngineBlocking()` | 引擎真的加载了，但 `state` 仍是 `UNLOADED` |
| 插件 → `notifyRequestSynthesis()` | 宿主 `startPreview` 发 `synthesize` |
| 插件 `synthesize` 里读 `state` | 不是 READY → 回 `NOT_READY` |
| 宿主 `onSpeakError` 收到 `NOT_READY` | 走保护逻辑：**自己 loadEngine + 记下 previewRetryPkg** |
| 插件加载完 → `onEngineReady` | 宿主看到 `previewRetryPkg == pkg` → **补发一次 startPreview** |

用户等的那 1~2 分钟里，插件其实已经算完一份了，宿主又让它算一份。

## 做法

**纯新增，不改 AIDL，老插件不受影响。**

### 1. 把实现从 binder 里提取出来

`loadEngine` / `closeEngine` 的函数体整段移到外围，变成
`doLoadEngine()` / `doCloseEngine()`；binder 里只剩两行转发。

这一步是**关键**：不是为了代码好看，而是为了让"宿主发起的加载"和
"插件发起的加载"**走同一份实现**。否则两套状态机各写一遍，迟早走岔。

### 2. 三个公开出口

```kotlin
protected fun requestEngineLoad(
    models: ModelBundle? = null,
    config: EngineConfig? = null,
): Boolean = doLoadEngine(
    models ?: lastHostModels,
    config ?: lastHostConfig ?: EngineConfig(),
)

protected fun requestEngineClose(): Boolean {
    if (state == EngineState.UNLOADED && !engineLoaded) return false
    doCloseEngine()
    return true
}

protected val pluginEngineState: Int get() = state
```

`doLoadEngine` 顺带改成返回 `Boolean`（真的发起了 / 幂等没动），
这样 `requestEngineLoad()` 能给出准确反馈。

### 3. 顺手补的一个陷阱：`models` 必须缓存

`requestEngineLoad()` 的默认参数是 `null`，但插件按钮点下去那一刻手上**没有**
`models` —— 那是宿主在 `loadEngine` 里传进来的。直接传 null 会把用户已经导入的模型
丢掉。

所以基类缓存宿主最近一次给的非 null `ModelBundle` / `EngineConfig`：

```kotlin
if (models != null) lastHostModels = models
if (config != null) lastHostConfig = config
```

**只存非 null** —— 宿主明确传 null 时（模型被删了）不能让旧值复活。

这个坑不补的话，新 API 看起来能用，但在"用户导入过模型"的场景下会静默走错分支，
比原来那个缺口更难查。

## 宿主侧要不要跟着改

不用。宿主那套「`NOT_READY` → 自动重载 + 补发」的保护逻辑**保留**——它兜的是
"插件进程被杀、引擎丢了"这种真实情况。插件改用 `requestEngineLoad` 之后，
这条逻辑不该再被触发；如果还在触发，说明插件仍在直接调 `loadEngineBlocking`。

## 验证

- `requestEngineLoad` / `requestEngineClose` / `pluginEngineState` / `lastHostModels`

  在 APK 的 `classes.dex` 里都能找到（`FOUND`）
- 重发 SDK AAR 后，`plugin-sdk-1.0.0.aar` 的 `classes.jar` 里
  `PonkoPluginService.class` 含这三个方法名
- 编译 `BUILD SUCCESSFUL`，零警告

真机判据（给插件侧）：装新包 + 新 AAR 重编的插件，点自绘的「加载模型」→
宿主那行应立刻变成"加载中"→ 加载完变"已加载"；点「开始推理」应**只出一份结果**。

---

## 一句话版

- **`protected` 的 `*Blocking` 不等于"插件能用的 API"** —— 它只是实现，
  状态机/前台服务/回调都在 binder 里，而 binder 是 private
- 判断"要不要提取实现"的标准：**这件事会不会有两个入口**。宿主一个、插件一个，
  就必须共用一份
- 给插件的新出口，默认参数要考虑"它那一刻手上有什么" —— 通常什么都没有，
  该由基类替它记住
- 这类缺口的症状会跑到很远的地方（"出来两份结果"），因为中间隔了三层：
  状态机 → 宿主保护逻辑 → 补发
