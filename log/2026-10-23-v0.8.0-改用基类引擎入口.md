# v0.8.0：改用基类的引擎入口，并给卡片加「关于」

宿主更新到 v12.2 / v12.3 之后的两件事。改的是一个我早就写进报告的缺口，和一行 manifest。

---

## 一、加载 / 释放改走 `requestEngineLoad` / `requestEngineClose`

### 现象

插件页自己画的「加载模型」点下去：

1. 插件页显示「已就绪 · 48 kHz · 6 线程」
2. 宿主功能区那行「引擎」**始终"未加载"**
3. 点「开始推理」，等 1~2 分钟，**出来两份结果**
4. 加载期间前台服务通知不出现

### 原因

`loadEngine` / `closeEngine` / `getStatus` / `isEngineReady` 全写在
`private val binder = object : IPonkoPlugin.Stub() { … }` 里，binder 是 private，
插件一个都拿不到。于是插件唯一的出路是直接调 `loadEngineBlocking()` ——
它只是**纯阻塞实现**，状态机在 binder 那侧：

| 步骤 | 发生什么 |
|---|---|
| 插件按钮 → `loadEngineBlocking()` | 引擎真的加载了，`state` 仍是 `UNLOADED` |
| 插件 → `notifyRequestSynthesis()` | 宿主 `startPreview` 发 `synthesize` |
| 插件 `synthesize` 里读 `state` | 不是 READY → 回 `NOT_READY` |
| 宿主收到 `NOT_READY` | 保护逻辑：自己 `loadEngine` + 记下 `previewRetryPkg` |
| 插件加载完 → `onEngineReady` | 宿主看到 `previewRetryPkg == pkg` → **补发一次** |

第 2~3 行本来就是"我算完一份了"，宿主再让它算一份 —— 用户白等一轮。

### 做法

宿主 v12.2 开了三个出口（`PonkoPluginService` 的 protected 成员，**不动 AIDL**）：

```kotlin
protected fun requestEngineLoad(models: ModelBundle? = null,
                               config: EngineConfig? = null): Boolean
protected fun requestEngineClose(): Boolean
protected val pluginEngineState: Int
```

插件侧的改动：

1. `loadFromUi()` 不再自己开线程，`requestEngineLoad()` 派发完立刻返回，
   真正的工作在基类 worker 上跑（和宿主功能区发起的那条**同一份实现**）。
2. 紧接着那一声 `notifySchemaChanged()` 是必需的：`requestEngineLoad()` 内部
   **同步**把 `state` 推到 `LOADING` 之后才派发，所以这一刻状态行能立刻写
   "正在加载…"、按钮能立刻变灰（`patch` 改不了 ACTION 的 `enabled`）。
3. `en_unload` → `requestEngineClose()`。返回 `false`（本来就没加载）时
   要把 `unloadingSince` 撤回去，否则按钮白灰一个 `UNLOAD_GRACE_MS`。
4. `engineLoading` 从一个自己维护的 `@Volatile var` 改成派生属性
   `pluginEngineState == EngineState.LOADING`。以前那个布尔只有插件页的加载
   线程会翻，宿主发起的加载它根本不知道 —— 两份状态迟早不同步。
5. 结束时的重画**没有**新增：成功路径在 `loadEngineInner` 末尾、
   失败路径在 `loadEngineBlocking` 的 catch 里，两条都在，而且宿主发起的加载
   也会经过它们。这是 v0.7.4 那次"失败原因可见"顺手留下的位置。

关于 `models`：`requestEngineLoad()` 不传参时用基类缓存的 `lastHostModels`。
本插件 `needsHostModels = false`、权重全在 `ModelStore` 里，`loadEngineBlocking`
根本不看 `models`，所以这里传不传都安全 —— 但**不传**比 `null` 更对：
基类只缓存非 null 的值，将来要是真用上宿主模型，也不会因为插件这边传了 null
把用户导入的 ModelBundle 丢掉。

### 验证

- 编译通过、零警告
- AAR 的 `classes.jar` 里 `PonkoPluginService.class` 含 `requestEngineLoad` /
  `requestEngineClose` / `pluginEngineState`（`FOUND`）
- 真机判据：点插件页「加载模型」→ **宿主那行「引擎」立刻变"加载中"、加载完变"已加载"**；
  点「开始推理」**只出一份结果**

## 二、卡片「关于」（`ponko.about`）

宿主 v12.3 起，卡片按钮行里多一个「关于」，内容来自 manifest：

```xml
<meta-data android:name="ponko.about" android:value="短文本" />
<meta-data android:name="ponko.about" android:resource="@raw/about" />
```

走 manifest 而不是 AIDL，理由里有一条对**用的人**比对我们更重要：
插件 stopped / 连接失败时也要能看 —— 那正是最想知道"这是什么、模型哪来的"的时刻。

这个插件写的是三句：

```
VoxCPM2 本地语音合成 · 需要 Ponko 2.0.0+（API 12）
权重不随 APK 分发，需自行下载或导入，遵循模型本身的许可
插件代码 MIT · github.com/visitor257/Ponko-EX
```

第一条就把"能不能商用"这个真问题顶到最前面。功能列表不用写 —— 卡片上已经列着了。

## 一句话版

- **`protected` 的 `*Blocking` 不等于"插件能用的 API"**：它只是实现，
  状态机 / 前台服务 / 回调都在 private binder 里
- 绕过状态机的代价不会立刻显现，它会跑到很远的地方发作（"出来两份结果"）
- 两个入口（宿主 / 插件）→ 必须共用一份实现，否则状态机走岔
- 派发型 API（返回 `Boolean`、立刻返回）之后要**马上重画一次**，
  因为状态在派发前就已经变了，而 `enabled` 只能靠整页重画
- 插件自己维护的状态标记，只要有一方看不见另一方的入口，就一定会分叉 ——
  能读基类的就别自己存
