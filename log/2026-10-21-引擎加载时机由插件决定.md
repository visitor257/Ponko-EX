# 2026-10-21 · 引擎什么时候加载，谁说了算

用户的一句话点醒的：

> 不应该打开插件页就自动加载模型，应该像 ponko 的对话和绘图那样要手动加载。
> **就算是自动加载，也是插件自己选择是否自动加载。**

## 现象

切到 Ponko-EX 页，插件刚连上，模型就开始加载。

用户只是想看"连上没"，结果后台开始干活。

## 原因

`PluginSession.onStateChanged` 里：

```kotlin
if (state == CONNECTED) {
    if (caps.contains(TTS) || caps.contains(TEST)) {
        conn.loadEngine(threads)     // 无条件
    }
}
```

注释写的理由是「刚连上就顺手把引擎加载好 —— 否则用户点试听还要多等一次加载」。

**这个理由在 Echo 上成立**：它 `loadEngineBlocking` 只是 `Thread.sleep(800)`，零内存。

## 为什么这是错的

写这行的时候，脑子里只有 Echo。但代码是给所有插件用的：

| | Echo | VoxCPM2 |
|---|---|---|
| 加载耗时 | 0.8 秒（假装） | 几十秒到分钟 |
| 内存 | 0 | 3.5 GB |
| 副作用 | 无 | 挤掉宿主的对话/绘图模型，可能 OOM |

宿主**不可能猜出**哪个插件是哪一档。它一律加载，等于把"用户没请求过的资源消耗"
变成默认行为 —— 而且用户没法拒绝，除非不进这一页。

这和「限 40 字」是**同一个错误的两面**：

- 那次是替用户决定"你不能输入多长"
- 这次是替用户决定"现在要不要花 3.5 GB"

共同点：**宿主用一个具体场景的约束，去规定所有人**。

## 做法：加一个能力常量

不动 AIDL、不抬版本号 —— `capabilities` 本来就是 `List<String>`：

```kotlin
object Capability {
    const val AUTOLOAD_ENGINE = "engine.autoload"
}
```

| 插件声明了 | 宿主行为 |
|---|---|
| 有 | 连上就加载 |
| 没有（默认） | 不加载，插件页出现「加载引擎」按钮 |

宿主侧：

```kotlin
val canAudio = caps.contains(TTS) || caps.contains(TEST)
val autoLoad = caps.contains(AUTOLOAD_ENGINE)
if (canAudio && autoLoad) conn.loadEngine(threads)
```

## 手动加载的 UI

仿 `MainActivity.toggleLoad()` —— 宿主自己的模型页就是一个按钮在加载/卸载之间切。

新增 `PluginConnection.engineReady()`：

```kotlin
fun engineReady(): Boolean = try {
    state == State.CONNECTED && plugin?.isEngineReady == true
} catch (t: Throwable) { false }
```

同步 AIDL 调用，插件侧保证 O(1)（只读 volatile）。这是宿主唯一能知道
"现在加载着没"的办法 —— `onEngineLoaded` 只在状态**变化**时来一次，页面重建后拿不到。

按钮文案跟着 `engineReady()` 走：「加载引擎」↔「卸载引擎」。

## 坑：改样式顺便把文字改了

`PluginUiPage.applyActionStyle()` 原来同时做两件事：

```kotlin
private fun applyActionStyle(tv: TextView, action: HostAction, enabled: Boolean) {
    tv.text = action.label       // ← 也从 def 里取初始 label
    // …配色
}
```

于是 `setActionEnabled("engine", true)` 会把已经改成「卸载引擎」的按钮
**冲回「加载引擎」**。表现是"点一下加载，字又变回去了"。

拆成两个函数：

```kotlin
private fun applyActionStyle(tv: TextView, enabled: Boolean)   // 只改样式
private fun applyActionText(tv: TextView, id: String, label: String)  // 只改文字
```

并用 `actionLabels` 记住当前文字。

**教训：一个函数只干一件事。** 混在一起时，调用方只想要其中一半，
却被迫接受另一半的副作用。

## 异步卸载的小问题

`closeEngine()` 是 `oneway`，插件在自己 worker 里才真正 free。
所以点完「卸载引擎」立刻问 `isEngineReady()`，读到的还是 `true`，按钮会白闪。

处理：延迟 250ms 再问一次状态。

不是优雅方案，但比"假装立刻好了"诚实 —— 界面上会显示"引擎仍在卸载中…"。

## Echo 声明了 AUTOLOAD_ENGINE

它是模板插件，加载免费、装上就该能试听。代码注释里写了判断标准：

> · Echo 的 loadEngineBlocking 只是 sleep 800ms，零内存 → 声明，装上就能试听
> · 真模型（几 GB、几十秒）→ **不要声明**，让用户自己点「加载引擎」

## 我自己犯的错：没提交就删 worktree

改完 Echo，跑 `git worktree remove --force`，源码改动跟着没了
（APK 已经编好，但源码丢了）。

`--force` 会丢弃未提交的改动，而我当时只想着"清理临时目录"。

**规矩：worktree 里的改动先 commit，再 remove。** 没有例外。

## 总结

这条能推广开：**默认值要按最坏情况定。**

- 假设插件很轻 → 对重插件是灾难性的
- 假设插件很重 → 对轻插件只是多一次点击

所以默认"不自动加载"，让轻插件自己 opt-in。这个方向的错误代价不对称，
选默认值的时候就该看这一点。

同一个思路可以回头看别的默认值：比如 `streamAudio` 默认 `false`、
`useGpu` 默认 `false` —— 都是同一个道理。
