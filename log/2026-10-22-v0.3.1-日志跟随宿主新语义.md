# v0.3.1：日志改成真追加，跟宿主的跟随规则对齐

宿主这一轮（`de4723f` / `a8f92d9`）修的是"日志一有内容，整页跳过去"，顺带把日志框的
滚动规则写成了契约：**追加时，只有用户本来就停在底部才滚到最新一行**，容差 8dp。
插件这边不改代码也能跑，但会跟这条契约打架 —— 所以有了 0.3.1。

## 宿主那侧到底改了什么

| 提交 | 内容 |
|---|---|
| `de4723f` | ① `fullScroll(FOCUS_DOWN)` → `scrollTo()`；② 日志正文与它的 ScrollView 显式 `isFocusable = false`（保留 `isFocusableInTouchMode`，长按仍能选/复制）；③ 跟随条件化（`isAtBottom()`，8dp 容差）；④ `appendLog` 里把外层整页的 `scrollY` 记下来再恢复 |
| `a8f92d9` | 文档把跟随行为写成契约，并记下 `fullScroll` 那个坑 |

真凶是 `fullScroll`：它内部走 `scrollAndFocus()` → `requestChildRectangleOnScreen()`，
**无条件**把日志矩形请求成可见并沿 View 树冒泡，外层整页 ScrollView 就跟着滚。
我之前那份报告把主因归到 `setTextIsSelectable` 的 `isFocusable`，方向对但不是主路径 ——
`fullScroll` 在 `render()` 里每个日志框都调一次，跟"每次状态刷新都跳"严格对应。

## 插件为什么要跟着改

宿主的新规则是给**追加**设计的。而 v0.3.0 推的是**整段快照**（`append = false`）：

- 用户停在底部 → 没问题，宿主替换完照样跟随；
- 用户翻上去看历史 → 位置不动，但**内容被整段换掉**（新的 120 行窗口整体后移），
  他正在看的那行没了。等于用另一条路径重犯了"抢走视线"。

所以改成**增量追加**：只送 `pushedLines` 之后的新行，`append = true`。

## 游标怎么保证不算错

差量推送必须知道"界面上已经有几行"，而这件事有两个会坏掉的时刻：

1. **缓冲裁剪**：`logLines` 满了 120 行会 `removeFirst()`，界面上那几行成了孤儿，
   差量算不出来。→ 裁剪时置 `logTrimmed`，下一次推送**整段重置**一次（把界面砍回 120 行）。
2. **页面重建**：`notifySchemaChanged()` 后宿主用 schema 里的 `value` 重建日志框，
   界面内容变回"当时那份快照"。→ `logSnapshotForSchema()` 在**同一把锁里**
   取快照并把 `pushedLines` 对齐到它的行数。
   - 先取快照、后记行数 → 中间插进来的一行会被当作"已送过"从此丢掉；
   - 先记行数、后取快照 → 重建后会重复推同一行。
   两者都必须避免，所以合成一步。

已知的极小残留窗口：补丁已经在途、而宿主正在处理 `getSettingsSchema()`，重建完成后
那条补丁才落地 → 重复一行。日志重复一行无害，比漏行好，也不再为它加序号机制。

## 顺带

README 中英同步加了一句"翻上去看历史不会被拽回底部"（这条是宿主的行为，插件只是不再
绕过它）。

## 还没修的（已写进给宿主的报告后记）

1. `render()` 里 `host.removeAllViews()` 前后没有保存/恢复外层 `scrollY`。
   状态刷新让内容**变短**时（下载区收成一行），`scrollY` 会被夹到新上限 —— 这是
   "整页往下掉一点"的另一条路径，和日志无关。
2. `logBlock()` 末尾 `scroll.post { scrollToBottom(scroll) }` 可能在首次测量之前执行，
   那时两个 height 都是 0，`target` 算成 0，日志框停在**顶部**；更糟的是
   `isAtBottom()` 从此返回 false，**后续补丁全部不跟随**（看起来像"日志不更新了"）。
