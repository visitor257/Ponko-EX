# 2026-10-21 · VoxCPM2 插件线（Ponko-EX_VoxCPM2）

第一条**真插件**线。Echo 那条只验链路，这条要真的出声。

分支从 `main` 派生，只 include `:plugins:voxcpm2`。

---

## 接口是照着 VoxCPM2 设计的，省了一大截

打开 SDK 源码才发现：`SynthesisRequest` 里的 `mode` / `referenceAudio` /
`referenceTranscript` / `voiceDescription` / `cfg` / `timesteps` / `seed` 全都是
为这个模型准备的（注释里直接写了 `voxcpm2_jni.cpp:211`）。

所以插件侧不用做任何"翻译层"，`req` 的字段一一对应原生 `nativeGenerate` 的入参。
**唯一要自己处理的**是 `voiceDescription` —— 它不是独立参数，而是要拼成文本前缀
`"(描述)正文"`，并且如果宿主传的正文已经以 `(` 开头就不能再拼（否则双前缀）。

## 坑 1：JNI 符号名和包名绑死了

原生库里的符号是**编译期写死**的：

```
Java_com_voxcpm_test_VoxCpm2Bridge_nativeInit
```

插件里的类在 `com.litertchat.plugin.voxcpm2`，名字对不上，`System.loadLibrary`
之后调用会直接 `UnsatisfiedLinkError`。

三条路：

| 做法 | 代价 |
|---|---|
| 插件里硬写 `package com.voxcpm.test` | 能用，但半年后没人看得懂为什么 |
| 复制一份 343 行的 cpp 改名字 | 两份副本必然漂移 |
| **同一份源，编译期换前缀** | 多编一个 cpp + 链接，几十秒 |

选了第三条。CMake 里加 `target_compile_definitions(... PONKO_PLUGIN)`，
源码里：

```cpp
#ifdef PONKO_PLUGIN
#define JNI_NAME(fn) Java_com_litertchat_plugin_voxcpm2_VoxCpm2Bridge_##fn
#else
#define JNI_NAME(fn) Java_com_voxcpm_test_VoxCpm2Bridge_##fn
#endif
```

### 这里踩了一个宏的坑，值得记住

第一版写的是"标准两级拼接"：

```cpp
#define JNI_NAME2(cls, fn) Java_##cls##_##fn
#define JNI_NAME(fn)       JNI_NAME2(JNI_CLASS, fn)
```

编出来 `nm` 一看全是 `Java_JNI_CLASS_nativeInit` —— **一个字面量 JNI_CLASS**。

原因：`JNI_NAME2` 里 `cls` 紧挨着 `##`，宏展开时**参数不做预展开**。
`JNI_NAME` 那层也救不了，因为它在 rescan 时把 `JNI_CLASS` 当普通实参交给了
`JNI_NAME2`，而 `JNI_NAME2` 因为 `##` 拒绝展开它。经典的"两级拼接要靠外层
先展开"的规则，在这里正好被 `##` 卡死。

**判据**：`nm -D --defined-only <so> | grep Java` 必须能数出 10 个自己的符号。
数不出来就是符号名不对，别去猜别的地方。

## 坑 2：下载不能占着 worker

基类的 `onActionInvoked` 是在**单线程 worker** 上跑的（`setSetting` 也是）。
第一版把 3.3 GB 的下载直接写在里面，结果是：下载跑着的时候，
「取消下载」这个 action 排在它后面，**永远轮不到** —— 用户点了没反应，
只能强杀插件进程。

改法：下载另开一条 `Thread`，`onActionInvoked` 立刻返回；
取消靠一个 `AtomicBoolean`，下载循环每 256 KB 检查一次。

进度回调约 400 ms 一次，直接 `notifySchemaChanged()` 会把整页刷崩，
所以外面套了一层 700 ms 节流（手册里写的是"别高频调"，这是具体做法）。

## 坑 3：许可上的实质缺口

`llama.cpp-omni` / ggml 是 **MIT**，静态链接进 `libvoxcpm2jni.so` 之后，
**分发 APK 就得随包附版权声明和许可全文**。原来的测试 APK 里一个字都没有 ——
自己装没事，发给别人就违约了。

这条线补了三处：

1. 仓库根 `LICENSE`（MIT，本来就该有）
2. `plugins/voxcpm2/NOTICE.md` —— 引擎 MIT 全文 + 权重 Apache-2.0 归属 + 修改声明
3. 插件界面里一个 `INFO` 项 —— 用户看得见的那一份（很多人只会看到界面）

顺手把下载源也分开了：默认走魔搭 `DennisHuang/VoxCPM2-GGUF`（仓库标了
apache-2.0），省 0.7 GB 的 `zerg13` 那个**没填 license 字段**，所以不做默认。

## 宿主 2.0.0 之后：契约从"声明"变成"真值"

宿主那条线补了四件事：`config.threads` 传真值、试听参数真的填 `mode` /
`referenceAudio` / `referenceTranscript` / `seed`、试听能中途停止、结果带时间戳存下来
并且 `debugInfo` 会显示在诊断区。对应的设计记录在 main 线的
`log/2026-10-21-试听取消与传参.md`，这里只说**插件侧真正要动的地方**。

核对下来，线程和参数容错当初就是按"字段可能不填"写的，没坏。要改的是三处：

### 1. 线程兜底在"自动"时反而退化

```kotlin
// 改前：用户选「自动」→ 宿主传 0 → 8 核机上只跑 4 线程
val threads = if (config.threads > 0) config.threads
              else min(4, Runtime.getRuntime().availableProcessors())

// 改后：和测试 App 一致
val threads = if (config.threads > 0) config.threads
              else (cores - 1).coerceIn(2, 6)
```

宿主给「自动」存的也是 `0`，所以这条兜底不是死代码 —— 用户点「自动」就会走到。
把 4 写成常量的时候没想到这一点。

### 2. 参考音频不能直接拿宿主的 FD 去解码

原来的写法看起来很省事：

```kotlin
fd.use { AudioUtil.toReferenceWav(it.fileDescriptor, wav) }
```

两个问题：

- **SAF 的 FD 未必能 seek**。`MediaExtractor.setDataSource(FileDescriptor)` 内部要
  随机访问，而用户在网盘里选的文件，provider 给的可能是管道 —— 直接解会失败，
  还只报一个含糊的 "decode failed"。
- 手册也明确要求：**先复制到自己目录，然后关掉自己那份**。宿主的 FD 指向用户的
  文档，随时可能失效，不能当模型输入用。

改成先落盘（64 MB 上限，参考音频只要 5~10 秒），再按路径解码：

```kotlin
val copied = ParcelFileDescriptor.AutoCloseInputStream(fd).use { input ->
    raw.outputStream().use { sink -> input.copyTo(sink) }
}
val ok = AudioUtil.toReferenceWav(raw.absolutePath, wav)
raw.delete()
```

⚠ **别把 `fd.use {}` 和 `AutoCloseInputStream` 叠着用** —— 两个都会关同一个
`ParcelFileDescriptor`，第二个抛 "already closed"。只留 `AutoCloseInputStream.use`。

### 3. `debugInfo` 现在是用户看得见的

以前只往里写参数，因为没人看。宿主加了诊断区之后，这里面最该有的是 **RTF** ——
"为什么这么慢"是唯一会被反复问到的问题。现在写的是：

```
voxcpm2 mode=1 src=licensed threads=7 cfg=2.0 steps=10 seed=0 sr=48000
text=23chars design=no audio=6.4s gen=94210ms rtf=14.72
```

长度和模式够了，**不写文本原文、不写路径** —— 用户能长按复制这段贴到 issue 里。

## 界面重做：把「操作台」改成「状态页 + 日志」（v0.2.0）

起因是一句"插件界面跟独立测试 App 差别很大"。查下来，**差别不在实现质量，在契约**：
独立 App 自己画整个屏幕；插件只交一份 `UiSchema`（键值对 + 12 种控件类型），
宿主 `PluginUiPage.kt` 按 Ponko 主题画。插件在另一个进程，Binder 传不了 View。

### 先说清边界，别浪费时间

| 想做的事 | 能不能 |
|---|---|
| 逐文件权重状态、设备信息、快照日志 | **能**，只是多写几条 `STATUS` / `INFO` |
| 精确数字输入（cfg / 步数） | **能**，用 `TEXT` 自己 parse + 校验 |
| 两个控件并排、分栏 | **不能**，要宿主加 `ROW_START`/`ROW_END` |
| 流式实时日志 | **不能**，schema 是拉取式的，每次重画整页 |
| 自定义配色 | **不能**，插件读不到 `PonkoTheme` |

> `UiSchema.kt` 的注释里也是这么写的（"嵌套布局、表格、自定义绘制刻意不做"），
> 并且明确否认存在 `advancedActivity` 逃生口 —— 那只是早期文档里的一句臆想。

### 顺手挖出来的宿主坑：intro 不解析 markdown

`plugin-guide.md` 第 9 节写着"intro 可以用 **粗体**、`代码`"，但宿主的
`hintText()` 就是 `text = t`，**没有任何 Spannable / Html 转换**。照着手册写
`**粗体**` 会在界面上原样显示成一堆星号。

→ 本插件的文案全部改成 `「」` 和换行，不用 `**`。手册那句要么实现、要么删掉（属 main 线）。

### 新结构（按使用顺序排，不按重要性）

```
运行状态      引擎 / 权重 / 存储 / 设备(核数·ABI·内存) / 上次合成 / 提示
1 · 权重      下载源 CHOICE、逐文件 STATUS(已就绪·断点·不完整·未下载)、
              进度条(有下载历史才出现)、下载/取消/删除、来源与许可说明
2 · 合成参数  语音设计描述、CFG(文本输入)、扩散步数(文本输入)、
              将使用(cfg/steps/线程)、速度警告
说明          参考音频要求、三种模式区别、许可与声音权益
日志          GROUP(可折叠)：最近 24 行 + 清空按钮
```

几个设计决定：

- **intro 第一句永远是"现在该干什么"**（还缺权重 / 已就绪可以试听 / 正在下载 %）。
  插件页比独立 App 少一大块操作区，用户进来最容易迷路的就是下一步。
- **数字从 `SLIDER` 换成 `TEXT`**。滑块按 step 吸附，2.25 这种值根本输不进去。
  校验和回显放在 `onSettingChanged`：非法输入不改值，但 `help` 里要写清"保留了 2.0"，
  不能默默吞掉（用户会以为改成功了）。
- **日志是插件自己攒的环形缓冲**（120 行，界面显示最后 24 行）。
  每 10% 下载才记一行 —— 界面重画是**整页重建**，跟着 400ms 的进度回调刷不划算，
  `notifyThrottled()` 也从 700ms 放宽到 1000ms。
- **设备信息不能现取**。`getMemoryInfo()` 是一次到 system_server 的 Binder 调用，
  而 `buildSettingsSchema()` 跑在宿主的 Binder 线程上 —— 在那儿做 IPC 会占掉宿主
  16 个 Binder 线程里的一个。所以缓存，只在 `onCreate` / 加载完 / 下载完 / 合成完刷新。
- **合成结束要主动 `notifySchemaChanged()`**。宿主在 `onResult`/`onError` 里只更新
  功能区的提示文字（`setDiagnostics`），**不会重画插件页** —— 不喊一声，日志会永远
  停在"开始合成"，"上次合成"那行也不会出现。

### 已知未解

- 下载中每 1 秒整页重建一次，用户如果正好在 cfg 输入框里打字，内容会被覆盖。
  宿主只对 `SLIDER` 做了拖动保护（`draggingKey`），`TEXT` 没有。
- 生成过程中日志不实时（只在开始/结束各一条），中途只看得到功能区的"已生成 X 秒"。

## 跟上宿主的「加载时机由插件决定」（v0.2.1）

宿主在 20:05 那批改动里把 `PluginSession.onStateChanged` 的自动加载收掉了：

```kotlin
val canAudio = caps.contains(TTS) || caps.contains(TEST)
val autoLoad = caps.contains(AUTOLOAD_ENGINE)      // 新增能力常量 "engine.autoload"
if (canAudio && autoLoad) conn.loadEngine(threads)
```

以前是「TTS 或 TEST 就无条件加载」，现在**默认不加载**，只有声明了
`AUTOLOAD_ENGINE` 才在连接时加载。没声明时宿主在功能区多一个「加载引擎 /
卸载引擎」按钮（`PluginConnection.engineReady()` 同步问插件）。
理由写在 `log/2026-10-21-引擎加载时机由插件决定.md`：宿主猜不出
「Echo 的 0.8 秒」和「VoxCPM2 的 3.5 GB」的差别，一律加载等于替用户花内存。

### 这条线要做的判断：不声明

`capabilities = listOf(Capability.TTS)` —— **保持不变，不声明 AUTOLOAD_ENGINE**。
按 `plugin-guide.md` §6.1 的判据（加载几秒以上 / 占几百 MB 以上 → 别声明），
这个插件是反面教材里的那一档。声明了反而会退回"打开插件页就灌 3.5 GB"的老问题，
而且宿主就不再给「卸载引擎」按钮，8 GB 机型没有手动腾内存的入口。

**行为上没变**：没声明 ≠ 用不了。点「试听」时宿主拿到 `NOT_READY` 会自动
`loadEngine` 并把这次试听补上（`previewRetryUsed` 保证只补一次，且每次用户
主动点试听都重置）。区别只是"什么时候付这几十秒"交回给用户。

### 改了四处（都是文案/刷新，没有逻辑改动）

1. **`closeEngineBlocking` 补 `notifySchemaChanged()`**。这条是真 bug：
   宿主点「卸载引擎」只调 `refreshEngineLabel()` 改自己的按钮文字，
   **不重画插件页**。不喊这一声，「引擎」行会一直写着"已就绪 · 48 kHz"，
   而引擎其实已经 free 了。
2. `st_engine` 的未加载状态从光秃秃的「未加载」改成
   「未加载 · 点上面『加载引擎』，或直接点『试听』」；权重没下完则显示
   「未加载 · 先下载权重」。新机制下"未加载"是**正常起点**，不写清下一步
   就会被当成故障。
3. `buildIntro` 的 `ready && !nativeReady` 分支同步改口（原文只说"点试听会自动加载"，
   现在多一条「加载引擎」的正路）。
4. 下载完成的 `dlNotice` 原文是"返回上一页再进来，引擎会自动加载"——
   **这句话在新机制下是错的**（退出重进不再触发加载），改成点「加载引擎」或「试听」。

### 顺带确认的两件事

- **API 版本**：新 AAR（20:14 重发）`API_VERSION = 2`、`API_WITH_SCHEMA = 2`。
  查了下 APK 里编进去的 `getApiVersion` 已经是 `const/4 v0, #int 2` ——
  这次重编不是为了过版本校验，纯粹是让文案和宿主对齐。
- **加载失败现在有重试入口了**。上一轮讨论"没有加载键、失败后只能退出重进"，
  宿主这次把这条路补上了：失败 → 功能区显示错误 → 再点「加载引擎」即可，
  不必退出插件页。

## 真机反馈两条：按钮行为与卸载（v0.2.2）

用户试完报了两个现象，都在问"是不是宿主的问题"。查下来：**都是，但插件侧有一处该补**。

### 一、「试听」按一次推理一次，不会重放

不是 bug，是宿主没有"重播"这个动作。`PluginPage.buildActions()` 给音频插件
固定四个按钮：

| id | 标签 | 行为 |
|---|---|---|
| `engine` | 加载 / 卸载引擎 | 引擎生命周期 |
| `preview` | **试听** | `session.speakTo()` → 合成 → 播放 |
| `stop` | 停止 | 取消当前请求 |
| `save` | 保存 | 把 `lastAudioFile` 复制到「音乐/Ponko」 |

`preview` 的 label 是**硬编码**的「试听」，help 里也写着"用上面填的参数合成一段音频"。
宿主其实已经存了 `lastAudioFile` / `lastAudioPkg`（不然「保存」没有东西可存），
但只用来给 save 判可用性 —— **没有「播放上次」这条路径**。

插件侧无解：插件只返回音频文件，播放由宿主做；也没有任何 UI 字段能改宿主按钮。

→ 要改只能宿主加一个 `id = "play"` 的动作（`lastAudioFile` 存在就播放，几行代码），
  或者把「试听」在已有结果时改叫「重新合成」，减少误解。属 main / 宿主线。

### 二、「卸载引擎」点了没反应，再点又变加载

归因：**宿主只抽查一次 + SDK 没有卸载回调**，两者叠加。

宿主 `toggleEngine(pkg, load = false)`：

```kotlin
setUiHint("正在卸载引擎，释放内存…")
session.toggleEngine(pkg, load = false)      // oneway，立刻返回
act.window.decorView.postDelayed({           // ← 只查这一次
    val still = session.engineReady(pkg)     // 同步问插件 isEngineReady()
    setUiHint(if (still) "引擎仍在卸载中…" else "引擎已卸载，内存已释放")
    refreshEngineLabel(pkg)                  // 只有这里会改按钮文字
}, 250)
```

而 SDK 的 `closeEngine()` 是往**单线程 worker** 里排队的：

- 空闲时：`closeEngineBlocking` → `nativeFree()` 释放 3.5 GB。几百毫秒量级，
  250 ms 那次抽查很可能**还没完成** → 读到 `READY` → 提示"仍在卸载中"，
  **按钮永远停在「卸载引擎」**（此后再没有任何时机刷新它）。
- 正在推理时更糟：worker 被 `synthesizeBlocking` 占着，要先
  `cancelFlag = true` → 插件的 poller 每 **400 ms** 才看一次 `out.isCancelled`
  → `nativeCancel()` → 原生逐块检查才退出 → 才轮到 free。这一段轻松几秒。

然后用户再点一次「卸载引擎」：`engineReady()` 这时已经是 `false`（卸载其实成功了），
宿主走 else 分支 → **调的是 loadEngine** → 3.5 GB 又灌回去。
现象就是"卸载不了，反而又加载了"。

**AIDL 里没有任何"卸载完成"的回调**（`IPonkoCallback` 只有 onEngineLoaded /
onEngineError / onStage / onAudioChunk / onError / onResult），宿主只能猜。

### 插件侧补的两处（不够，但比原来诚实）

1. `engineUnloading` 标志：「引擎」行在释放期间显示「正在释放内存…」。
   原来那几百毫秒里宿主功能区在说"正在卸载"，插件页却已经写"未加载 · 点加载"，
   两边自相矛盾。
2. 卸载完成后**延迟 600 ms 再** `notifySchemaChanged()`。
   原来是在 `closeEngineBlocking` 内部立刻通知，而 SDK 是在它**返回之后**才把
   state 设成 UNLOADED —— 通知太早，宿主那边读到的还是 READY。

### 根治要宿主做（三选一，按代价排）

1. `closeEngine` 之后**轮询**到状态变化（250 ms 起，最多 3 s），别只查一次 —— 宿主侧几行
2. 插件页重画时顺手 `refreshEngineLabel()` —— 插件已经在卸载完后通知了，能吃到
3. `IPonkoCallback` 加 `onEngineUnloaded`（最干净，但要动 AIDL + 重发 SDK）

另外「试听」按钮的措辞/重播能力也属宿主。这三条都写在
`doc/plugin-guide.md` 的建议清单里比较合适，不该只有这条分支知道。

## 跟上宿主的三条修复 + SDK v3 按钮文案（v0.2.3）

宿主在 02:02 / 02:35 有两个提交，第一个把我上一份反馈里的三条全修了，第二个新加了
「插件可以给宿主按钮改名」的能力。

### 宿主改了什么

| 提交 | 内容 |
|---|---|
| `9c5faf9` | 卸载改成轮询 `getStatus().state` 到 UNLOADED（原来只查一次 250 ms）；新增「播放」动作 + 有产物时 preview 改名；SDK 用独立的 `closing` 标志，卸载窗口内 `synthesize` 回 `NOT_READY` 而不是 `BUSY`；`hintText()` 开始解析 `**粗体**` 和 `` `代码` `` |
| `7fdf5d6` | **SDK v3**：`IPonkoPlugin.getActionLabels()`，插件可改宿主按钮的文字 |

`getActionLabels()` 没有做成 manifest 字段，理由写在 `docs/plugin-sdk.md`：
`PluginManifest` 是 `@Parcelize`，`CREATOR` 按固定顺序读，老插件少写一个字段，
新宿主会读到 Parcel 末尾之外抛异常 —— 等于**所有插件必须同时重编**，
正是版本机制想避免的事。所以新方法加在 AIDL 末尾，宿主按
`pluginApi >= API_WITH_ACTION_LABELS` 决定要不要调。

约束：只改文字；key 不认识 / 空值 / 超过 12 字符 → **整个丢弃**（不截断），
其它项照常生效；方法抛异常 → 全部退回默认，**不影响连接**。

### 这条线怎么用

`buildActionLabels()` 覆写五个：

| key | 宿主默认 | 这里 |
|---|---|---|
| `engine.load` | 加载引擎 | **加载模型** |
| `engine.unload` | 卸载引擎 | **释放模型** |
| `preview` | 试听 | **合成语音** |
| `preview.again` | 重新合成 | **再合成一次** |
| `play` | 播放 | **重放** |

理由各一条：加载的是 3.5 GB 的**模型**，不是抽象的"引擎"；卸载后文件还在磁盘上，
「卸载」容易被理解成卸载插件，所以叫「释放」；「试听」实际要跑 1~2 分钟推理，
叫「合成」才不会再让人以为只是放声音；「重放」强调**不重新推理** —— 这正是
上一版真机反馈里最费解的那件事。

停止 / 保存用宿主默认。

### ⚠ 兼容性：这版插件要求新宿主

`API_VERSION` 从 2 抬到 3，而宿主是**严格区间校验**（`PluginConnection.kt:225`）：

```kotlin
if (api !in API_MIN_SUPPORTED..API_MAX_SUPPORTED) { setState(FAILED, "插件 SDK v$api 不兼容…"); return }
```

老宿主（`API_MAX_SUPPORTED = 2`）会**直接拒绝绑定**，不是降级成默认按钮。
所以宿主和插件必须一起更新，README 里写了这一条。

> 如果以后要让插件同时兼容老宿主，只有一个办法：不覆写 `buildActionLabels()`，
> 继续用 v2 编译 —— 但那样就拿不到改名能力，两个目标互斥，这是版本机制本身的取舍。

### 文案同步（不改会自相矛盾）

按钮改名之后，插件里的**所有**文案都得跟着改，否则界面在指一个不存在的按钮：

- 「未加载 · 点上面「加载引擎」，或直接点「试听」」→ 加载模型 / 合成语音
- 下载完成的提示、intro 的 `next` 分支、下载源 help
- **删掉一句已经失效的话**：上一版写着"每次点「试听」都会重新推理一遍 —— 宿主不缓存
  上一次的结果"。宿主现在有「重放」了，这句是错的，改成区分「合成语音」与「重放」

### 顺带

- **intro 第一句加粗**。宿主 `hintText()` 已经支持 `**粗体**`，「现在该干什么」那句
  用加粗更抓眼。上一版因为不解析才全改成「」和换行 —— 那条限制现在没有了。
- 补回一条被弄丢的警告：「**手机纯 CPU 推理，很慢**：5 秒语音约 1~2 分钟」
  （v0.2.0 重做界面时漏了，独立版一直有）。
- 「卸载后延迟 600 ms 再通知」保留，但注释改成"只给插件页自己用"——
  宿主现在自己轮询状态，不再依赖这一声。

## 跟宿主「合成与播放拆开」（v0.2.4）

宿主 `fa87165`（10:12）把我上一版刚适配的东西改掉了 —— **不是回退，是把根因修了**。

### 改了什么

| 之前 | 现在 |
|---|---|
| 合成完自动播放 | **合成只落盘、不出声**；要听点「播放」 |
| `preview` key，默认「试听」 | `reasoning` key，默认「合成」 |
| `preview.again`（有产物时改名「重新合成」） | **删掉**，key 从七个减到六个 |
| 面板标题「试听参数」 | 「合成参数」 |
| 动作 id `preview` | `reasoning` |

宿主的锚点：**「合成」是产出，「播放」是消费**。绑在一起有三个后果 ——
强迫消费（只想生成不想听，安静场合没法用）、按钮含义漂移（所以才有 `.again`）、
停止成了逃生口（用户想的是别播，而停止的语义是丢弃这次结果）。
所以 `.again` 不是需求，是自动播放打的补丁。

「试听」这个名字也有实害：点完没声音，用户以为坏了，而音频已经在那儿等着播了。

### 这条线跟着改的

1. **`ActionLabel.PREVIEW` → `ActionLabel.REASONING`，删掉 `PREVIEW_AGAIN` 那行。**
   新 AAR（10:05 重发）里旧常量已经不存在，不改**根本编不过** —— 这次是被编译器
   按着改的，不是可选项。
   `API_VERSION` 仍是 3（宿主那边 v3 还没发出去，所以直接换了字符串值，不留别名）。
2. **`PLAY` 的覆写去掉，回到宿主默认「播放」。** 上一版叫「重放」是为了强调
   "不重新推理"，现在合成/播放本来就是两个按钮，这个区分由结构承担；
   而且宿主的完成提示是「已生成 X 秒音频，点「%s」试听」，往里填「重放」
   会变成"点「重放」试听" —— 第一次听哪来的"重"。少覆写一个，也少一处会漂的字。
3. **说明区必须写"合成不会自动出声"。** 这是拆分唯一要付的价：多点一下。
   宿主自己的提示写了，插件页也写一遍 —— 插件页有自己的一屏说明，用户不一定
   回头看上面那行提示。改动落在「说明」最后一段：
   「合成语音」只跑推理、产出文件，**不会自动出声** —— 合成完点「播放」才听得到。
4. **intro 的"已就绪"分支**补半句"合成完再点「播放」"。
5. README 中英：按钮表从"五个按钮（含再合成一次/重放）"改成"一个动作一个按钮"，
   参数区标题改「合成参数」，「已知限制」里「重放只留最近一份」改「播放只有最近一份」。

`preview.again` **0** 处、`再合成一次` **0** 处 —— 旧 key 确实没跟着编进来。

### 观察
