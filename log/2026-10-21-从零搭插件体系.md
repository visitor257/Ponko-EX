# 2026-10-21 · 从零搭插件体系

从「决定走插件 APK 这条路」到 Echo 测试插件真机出声、界面能进，
一天之内撞上的问题。按撞上的顺序记，不是按重要性。

---

## 0. 为什么是插件 APK

先花了大半天确认别的路都走不通：

| 方案 | 结论 |
|---|---|
| 让用户往手机里丢 `.so`，Ponko 加载 | ❌ Android 10+ 禁止应用 `dlopen` 自己目录里的可执行文件 |
| 把 `.so` 放进 assets，运行时解压再加载 | ❌ 同上，解压出来仍然不可执行 |
| 导源码在 App 内编译 | ❌ 手机上没编译器，也没 JDK |
| **插件 APK** | ✅ 只有它：系统在**安装时**把 `jniLibs` 释放到 `nativeLibraryDir`，那里允许加载 |

关键认知：**能不能加载，取决于文件是不是安装时由系统放的**，不取决于权限。
所以"用户自己放"这件事系统层面就封死了，没有绕过的方法。

顺带一个推论：用户装的必须是**编译好的包**，不是源码。这决定了插件分发形态。

## 1. 中文路径 → AGP 直接拒绝

### 现象
```
Your project path contains non-ASCII characters.
```
构建连配置阶段都过不去。

### 原因
AGP 对含非 ASCII 字符的工程路径直接拒绝（不是警告，是硬失败）。

### 做法
两个层面都做了：

1. `gradle.properties` 里 `android.overridePathCheck=true` —— 让**配置**能过
2. 真正构建放到纯 ASCII 目录（当时先复制到一个沙箱，后来工程整体
   搬到了纯 ASCII 路径，就不用沙箱了）

**教训**：`overridePathCheck` 只骗过检查，不代表构建真的没问题。
真正的解法是路径本身干净。

## 2. `gradlew` 用不了

### 现象
`./gradlew assembleRelease` 卡住，或者报找不到 distribution。

### 原因
本机 `~/.gradle/wrapper/dists` 是空的，wrapper 从没下过 distribution。
而机器又没稳定的外网。

### 做法
一律直接调本机 gradle：
```bat
C:\gradle\gradle-9.7.1\bin\gradle.bat
```
**不要用 gradlew**，也不要试图"先跑一次 gradlew 让它自己下"。

## 3. `.bat` 里的中文注释让脚本自己刷了 22 MB 日志

### 现象
构建脚本执行后疯狂输出同一段内容，日志涨到 22 MB，得手动杀掉。
内容看起来是脚本自己在反复调用自己。

### 原因
cmd.exe 按 **OEM 代码页（本机是 GBK）** 解析 `.bat`。我存的是 UTF-8 中文注释，
被按 GBK 读出来是乱字节，其中某些字节序列把换行吃掉或把 `if` 块的括号结构破坏，
于是流程跳到了不该去的地方，形成循环。

### 做法
**`.bat` 一律纯 ASCII**，注释全写英文。
`build.bat` 开头现在有一句：
```
REM Why no Chinese characters in this file: ...
```
就是为了拦住未来的我。

### 反过来：`.ps1` 必须带 UTF-8 BOM
PowerShell 5.1 读**无 BOM**的 `.ps1` 会按 GBK 解析，中文注释同样崩。
写 `.ps1` 用：
```powershell
[IO.File]::WriteAllText($f, $t, (New-Object Text.UTF8Encoding($true)))
```
`$true` 就是"带 BOM"。

**两个脚本类型的要求正好相反，特别容易记反。**

## 4. `robocopy /PURGE` 把沙箱里的东西删了

### 现象
同步源码到沙箱后，`_dist` 目录（已经签好名的 APK）、构建脚本、插件的 build 产物全没了。

### 原因
`/PURGE` 的意思就是"删除目标端所有源端没有的文件"。而 `_dist`、构建脚本
当时只存在于沙箱里，源码树里没有 → 全被当垃圾清了。

### 做法
同步**不带 `/PURGE`**。构建脚本收进源码树的 `tools/`，这样两边都有。

**教训**：`/MIR` 和 `/PURGE` 在"目标是工作目录、不是纯镜像"的场景下是危险开关。
想清垃圾就手动清，别用镜像模式。

## 5. AGP 9.x 默认关掉了 AIDL

### 现象
一堆 `Unresolved reference: IPonkoPlugin`、`Unresolved reference: Stub`，
但 `.aidl` 文件明明在 `src/main/aidl/` 下面放着。
关键是**报错完全不提原因**，看起来像路径配错了。

### 原因
AGP 9 起 `aidl` 是默认关闭的构建特性（为了加快配置阶段）。

### 做法
```kotlin
android {
    buildFeatures {
        aidl = true
    }
}
```
加在**宿主和插件两个工程**里（谁用 AIDL 谁加）。

**这个坑特别值得记**：错误信息离原因太远，第一次查了很久。

## 6. 插件工程不能 `project(":ponko-plugin-sdk")`

### 现象
插件 module 里写 `implementation(project(":ponko-plugin-sdk"))`，Gradle 说找不到这个 project。

### 原因
`project(...)` 只在**同一个 Gradle 构建**里有效。插件是独立工程，
SDK 那个 module 根本不在它的 settings 里。

### 做法
宿主把 SDK 发布成 AAR 到本地 maven：
```bat
tools\build-android.bat :ponko-plugin-sdk:publishReleasePublicationToLocalRepoRepository
```
插件侧：
```kotlin
implementation("com.litertchat.ponko:plugin-sdk:1.0.0")
```

## 7. 改了 AIDL 却没重发 AAR → 运行时 `NoSuchMethodError`

### 现象
编译全过，装上去一点就崩：
```
java.lang.NoSuchMethodError: No interface method getSettingsSchema()...
```

### 原因
宿主里改的是 SDK **源码**（`project(":ponko-plugin-sdk")` 直接编），
马上就能用；但插件消费的是 **maven 里的 AAR**，还是旧的。
两边看到的接口不是同一个。

### 做法
记牢这条流程：

```
改 AIDL / Parcelable
  → 重发 SDK AAR
  → 重编插件
  → 重装两个 APK（都装，宿主可能也要）
```

**只重编宿主是完全没用的**。反过来也只重编插件没用（宿主还在旧接口上）。

> 这次的「第二次试听报引擎未加载」就是同类问题的一个变种：改的是 SDK **基类实现**
> （不是接口），但如果只重编宿主、不重编插件，插件里跑的仍是旧基类 —— 一模一样要两个都重编。

## 8. `SecurityException`

### 现象
```
java.lang.SecurityException: Permission Denial: binding to
com.litertchat.plugin.echo/.EchoPluginService requires
com.litertchat.ponko.permission.BIND_PLUGIN
```

### 原因
三种可能，按概率排：

1. **两个 APK 不是同一把密钥签的** —— 最常见
2. 宿主自己没拿到那个 signature 权限（新装/重启前后偶发）
3. 权限声明方向搞反了

### 做法
1. 用宿主同一个 `ponko-release.jks` 签插件，比对证书指纹（`apksigner verify --print-certs`）
2. 宿主 Manifest **同时**声明 `<permission>` 和 `<uses-permission>`
   （只写 permission 是"我定义它"，不算"我持有它"）
3. 插件在 `<service>` 上写 `android:permission` —— 它约束的是**调用方**

### 顺手做的
宿主界面加了「环境自检」一行，直接显示：
- 宿主自己有没有拿到 bind 权限
- 宿主证书指纹前 8 位
- 插件证书指纹前 8 位

出问题时**第一眼就能分清是"权限没生效"还是"签名不一致"**，不用再来回猜。

## 9. `bindService` 返回 false —— 最阴的一个

### 现象
`bindService(...)` 返回 `false`。没有异常、没有报错，
系统日志里只有一句：
```
Unable to start service Intent { act=com.litertchat.ponko.PLUGIN pkg=... }: not found
```
而 `PackageManager` 明明能查到那个 service。

### 原因
**新安装的包处于系统的 stopped 状态**（`FLAG_STOPPED`）。
这个状态下别的应用 bind 它的服务会**静默失败**，返回 false。

### 试过无效的（记下来省时间）
| 做法 | 结果 |
|---|---|
| 发广播 | ❌ 系统默认排除 stopped 包（`FLAG_EXCLUDE_STOPPED_PACKAGES`） |
| `startService` | ❌ 不清标记 |
| `pm enable/disable` | ❌ 不动标记 |
| 重装同一个 APK | ❌ 不动 |

Android 15 起官方更明确：**只能由用户的直接或间接操作解除**。

### 做法
插件必须有一个 Activity，并且被**启动一次**。

然后设计成用户无感：
1. 用户点卡片上的「启用」
2. 宿主检测到 stopped → 自动 `startActivity` 插件的一个**无界面** Activity
3. 那个 Activity 立刻 `finish()`，用户只看到一闪
4. 回来 `onResume` 自动重连（另有 900ms 延迟兜底）

**用户只按了一次键。**

## 10. 插件要在桌面隐藏，又必须能被启动

这两个要求一开始以为矛盾：没有 LAUNCHER 就启动不了，有 LAUNCHER 就有图标。

### 实际不矛盾
清 stopped 只要求「**某个组件**被启动」，不要求那个组件**对用户可见**。

### 做法
插件里放一个继承 `PonkoActivatorActivity` 的 Activity：

```kotlin
class EchoActivator : PonkoActivatorActivity()
```

Manifest：
```xml
<activity
    android:name=".EchoActivator"
    android:exported="true"
    android:excludeFromRecents="true"
    android:noHistory="true"
    android:taskAffinity=""
    android:theme="@android:style/Theme.NoDisplay">
    <intent-filter>
        <action android:name="com.litertchat.ponko.ACTIVATOR" />
    </intent-filter>
</activity>
```

- **没有 `CATEGORY_LAUNCHER`** → 桌面无图标（aapt 查过：确实没有 `launchable-activity`）
- `Theme.NoDisplay` + 基类 `onCreate` 立刻 finish → 连闪都没有
- 自定义 action 让宿主仍能发现并启动它

### 一个坑中坑
构造启动 Intent 时**故意不加 `CATEGORY_LAUNCHER`**：
```kotlin
Intent(Intent.ACTION_MAIN).setClassName(pkg, targetActivity)
```
目标如果只声明了自定义 action，带上 LAUNCHER category 在部分 ROM 上会匹配失败。
显式 `ComponentName` 启动**不检查 intent-filter**，所以能起来。

## 11. 卡片"收起"了却还是那么高

### 现象
点标题，文字确实消失了，但卡片高度一点没变，还是占大半个屏。

### 原因
色条是用 `FrameLayout` + 一个 4dp 宽、`height=MATCH_PARENT` 的裸 `View` 做的。
而 `View.getDefaultSize()` 在 **AT_MOST** 模式下返回的是 `specSize` ——
也就是父容器给的**整个可用高度**。

`wrap_content` 的 FrameLayout 传给子 View 的正是 `AT_MOST(可用高度)`，
于是那条"4dp 色条"实际高度 = 满屏，把卡片顶成满屏高。
收起时文字没了，但这个满屏高的空壳还在。

### 做法
**色条画在背景里**，不占布局：
```kotlin
// Drawable 里 clipRect 裁出左边 4dp，再 drawPath 一个圆角
override fun draw(canvas: Canvas) {
    surface.draw(canvas)
    canvas.save()
    canvas.clipRect(bounds.left, bounds.top, bounds.left + stripeW, bounds.bottom)
    canvas.drawPath(path, paint)
    canvas.restoreToCount(save)
}
```
背景的 `bounds` 天然等于视图自己的尺寸，和布局测量完全无关。

**教训**：`wrap_content` 容器里别放 `MATCH_PARENT` 的裸 View。
`getDefaultSize` 在 AT_MOST 下的行为是 Android 里反复坑人的老问题。

## 12. 分隔线高度变成 0（隐形）

### 现象
加了 `divider()`，看不见。

### 原因
`divider()` 内部设了 `layoutParams`（高度 `dp(1)`），但调用处是：
```kotlin
addView(divider(), matchWrap())      // matchWrap 高度 = WRAP_CONTENT
```
`addView` 传的 LayoutParams **覆盖**了 View 自己那份。而 `LinearLayout`
对高度 `WRAP_CONTENT` 的 View 测量结果是 0（它没有内容）。

### 做法
显式传高度：
```kotlin
addView(divider(), LinearLayout.LayoutParams(MATCH_PARENT, dp(1)))
```

**教训**：`addView(v, lp)` 里的 `lp` 永远赢。View 自己设的 `layoutParams` 只在
`addView(v)` 不带 lp 时才可能生效，而且经常也不生效（取决于父容器）。

## 13. 卡片下面一块"来路不明的灰"

### 现象
最后一张卡片和底部菜单之间有一片灰色，看起来像多画了一个框。

### 原因
两个因素叠一起：

1. 根容器的 `LinearLayout` **没设背景** → 露出 `ScrollView` 的底色
2. `ScrollView.isFillViewport = true` → 内容不足一屏时把 root 拉到满屏

于是"内容结束到屏幕底部"那一段就是 ScrollView 的底色，和卡片的白形成色差。

### 做法
root 显式设背景（和 ScrollView 同色）：
```kotlin
setBackgroundColor(pal.bg)
```
另外把页面末尾那段说明文字包成 `surface` 圆角的卡片 —— 有明确边界之后，
即使有色差也读得懂"这是一块区域"，而不是"这里出了 bug"。

## 14. 卸载点了没反应（两次）

### 现象
第一次：`AlertDialog` 弹了确认框，点"卸载"什么都没发生。
第二次：改成直接 `ACTION_DELETE` Intent，还是什么都没发生。**无异常、无日志。**

### 原因
没查出来。`startActivity` 不抛异常但界面不出现，可能是 ROM 裁了这个
Intent handler，也可能和对话框主题有关。

### 做法
**换成一条最不容易失效的路**：跳系统的「应用信息」页。
```kotlin
Intent(Settings.ACTION_APPLICATION_DETAILS_SETTINGS,
       Uri.parse("package:$pkg"))
```
- 所有 Android 设备都有这一页，不存在被裁
- 卸载和二次确认都由系统负责
- 和"跳设置"是同一类调用，不依赖对话框主题

再加一个兜底：`ACTION_APPLICATION_DETAILS_SETTINGS` 起不来就退到
`ACTION_APPLICATION_SETTINGS`（应用列表），用户还能手动找到。

### 更底层的教训
**"点了没反应"这种 bug，先给点击加即时反馈**。现在是 `RippleDrawable` 水波纹，
点下去有视觉变化 —— 至少能分清"没点中"和"点中了但流程挂了"。
没有反馈的时候，这两种情况在用户眼里完全一样。

## 15. 试听第二次报「引擎尚未加载」

### 现象
第一次点「试听」正常出声。再点一次，界面立刻显示「引擎尚未加载」。
但插件自己的界面里引擎状态还写着"已就绪"。

### 原因
SDK 基类合成收尾时这样写：
```kotlin
state = if (modelBytes > 0) EngineState.READY else EngineState.UNLOADED
```
拿「模型体积」当「引擎是否还加载着」的判据。
Echo 没有模型文件，`modelBytes` 恒为 0 → **第一次合成一成功，状态就被重置成
UNLOADED**。第二次 `synthesize()` 检查 state 不是 READY，直接回 `NOT_READY`。

### 做法
SDK 加独立的 `@Volatile engineLoaded` 标记：
- 加载成功 → true
- 加载失败 / `closeEngine` / `onDestroy` → false
- 收尾改成 `if (engineLoaded) READY else UNLOADED`

宿主侧也加了一层兜底：收到 `NOT_READY` 时自己重载一次引擎，
加载完**把这次试听补上**（`onEngineReady` + `previewRetryUsed` 保证一次点击只补一次，
防"加载失败→重试→又失败"打转）。

### 教训
**`modelBytes` 只是显示用的数字，不是状态。** 任何"用体积判断是否活着"的写法都要警惕 ——
零体积的东西（无模型的插件、空文件、空集合）会让这类判据悄悄失效。

## 16. Android 14 拒绝启动前台服务

### 现象
`startForeground` 抛异常，或者服务直接起不来。

### 原因
两个要求：
1. `AndroidManifest` 里 `<service>` 必须有 `foregroundServiceType`
2. 用 `specialUse` 时必须声明 subtype 说明用途

### 做法
```xml
<service android:foregroundServiceType="specialUse" ...>
    <property
        android:name="android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE"
        android:value="Runs local speech synthesis requested by Ponko" />
</service>
```
加上对应权限 `FOREGROUND_SERVICE_SPECIAL_USE`。

## 17. 前台服务要在 `onBind` 里起，不能等到推理时

### 决策记录（不是 bug，是差点写错的地方）
Android 12+ 禁止**后台**启动前台服务。推理可能跑 1-2 分钟，用户中途切走很正常。

如果等到 `synthesize` 里才 `startForeground`，那时宿主可能已经不在前台 →
`ForegroundServiceStartNotAllowedException` → 服务起不来 → 推理被杀。

### 做法
在 `onBind` 里就起。那一刻宿主刚 `bindService`、一定在前台，必然能过。
通知文案先写"准备中…"，后面随阶段更新。

## 18. 音频传不回来：路径和控制块都不行

### 现象 / 三个候选方案
| 方案 | 结果 |
|---|---|
| 把文件路径传回宿主 | ❌ 宿主读不到插件的私有目录（沙箱隔离） |
| 塞成 `ByteArray` | ❌ 长了必崩：Binder 全进程只有 **1 MB** 配额 |
| **`ParcelFileDescriptor`** | ✅ 传的是文件句柄，不受体积限制 |

### 做法
插件写到自己的 `cacheDir`，`ParcelFileDescriptor.open(f, MODE_READ_ONLY)`
填进 `ResultBundle.audio`。宿主 `FileInputStream(fd).readBytes()` 读完关掉 FD。

小结果（< 256 KB）也支持 `inlineAudio` 直接内联，省一次 FD —— 但别拿它传长音频。

### 另一个坑：宿主不直接用 `MediaPlayer.setDataSource(fd)`
WAV 需要精确的 offset/length，FD 跨进程传递后长度信息不一定可靠，
表现是"播不动但不报错"。改成**先把 FD 内容复制到自己的缓存文件再播**，
几 MB 的开销可以忽略。

## 19. `oneway` 回调没背压，`onStage` 差点刷爆 Binder

### 现象
（预判 + 设计时拦住的）插件在耗时循环里每个 token 都调一次进度回调。

### 原因
`oneway` 调用不等返回，但消息会在接收方排队。发太快会吃满宿主那 1 MB
Binder 配额，连累宿主所有其它 IPC，表现是"整个 App 卡一下"。

### 做法
SDK 的 `Emitter.stage()` 内置 **500ms 限流**（同阶段内的重复调用直接丢弃，
阶段切换立刻发）。`onAudioChunk` 限制 ≤ 64KB/块且只在 `streamAudio=true` 时用。

**别绕过 `Emitter` 自己调 `onStage`。**

## 20. AIDL 新方法必须加在末尾

### 原因（没出事，但差点）
Binder 事务码按**方法声明顺序**分配。在文件中间插入一个新方法，
后面所有方法的事务码整体后移。

老插件（用旧 AIDL 编的）收到新宿主发来的码，会按**自己的**顺序去执行 ——
本来是 `getStatus`，结果执行了 `closeEngine`。

**这比直接报错糟糕得多**：不报错、看起来"能用"，但行为诡异地错位。

### 规矩
所有 `IPonkoPlugin` / `IPonkoCallback` 的新方法，**永远追加在文件最末尾**。
注释里也写了这句。

## 21. 判断"能不能调"要靠版本号，不能靠 try-catch

### 原因
AIDL 遇到不认识的方法时，行为**没有保证**：
- 同步方法可能读到空 Parcel，返回 `null` 或怪值
- `oneway` 方法**静默无操作**，连异常都没有

所以 try-catch 兜不住。宿主必须用 `pluginApi >= API_WITH_SCHEMA` 这种版本判断
来决定要不要调。

## 22. 插件被系统"后台限制"禁用

### 现象
插件装在系统里，`PackageManager` 也能查到包，但 service 解析不到。

### 原因
部分 ROM（尤其国产）会给应用加"后台限制/省电策略"，把 service 组件禁掉。
这不是 stopped 状态，是组件级别的禁用。

### 做法
宿主诊断里区分了这几种：
- 包没装 / 已被卸载
- 包在但**被系统停用**（`ApplicationInfo.enabled == false`）
- 包在、enabled，但**服务解析不到**（后台限制）
- 服务能解析，但 **stopped**（需要激活）
- 都能，但 bind 抛 `SecurityException`（签名）

每种给不同的提示文案，而不是统一说"连接失败"。

## 23. 相邻两版 APK 字节数完全相同

### 现象
改了代码，重新构建，`ls -l` 显示字节数一模一样。
一度以为构建没生效（改的是 `modelBytes` 判据那一版）。

### 原因
巧合 + 压缩后大小接近。**字节数相同不代表内容相同。**

### 做法
判包一律看 **sha256**：
```bash
sha256sum Ponko-2.0.0.apk
```
唯一的例外是"体积明显不同"，那至少能确认是不同构建，但**相同体积什么都不能说明**。

（这次连续三版都是 63,654,271 B，全都不一样。）

## 24. 增量打包缓存损坏

### 现象
`:app:packageRelease` 报 `IncrementalSplitterRunnable` 失败，
APK 只写了 54 MB（正常 63 MB）。

### 原因
增量打包缓存损坏，不是磁盘不足。

### 做法
删掉这两处再重编：
```
app/build/outputs/apk/release
app/build/intermediates/apk
```

## 25. 判据：交互必须有即时反馈

这条不是具体 bug，是一天下来的总结。

出现过的"点了没反应"：
- 卸载按钮点了不弹框（第 14 条）
- 点「启用」后插件闪一下，状态没变（实际是在等激活）

共同点：**用户看不到任何变化，就无法区分"没点中"和"点了但失败了"**，
于是只能反复点，或者干脆认为功能坏了。

### 做法
- 按钮加 `RippleDrawable` 水波纹
- 状态文字统一走一个 `setUiHint()`，凡是发起动作就先写"正在…"
- 卡片左侧色条表示状态（绿=就绪、黄=待处理、红=失败、灰=未启用）

**色条尤其重要**：卡片收起时只剩一行字，颜色是唯一的状态信号。

## 收尾

一天里最贵的三课：

1. **`bindService` 返回 false 大概率是 stopped**，别去查权限
2. **改了 SDK 就必须重发 AAR + 重编插件**，只重编一边等于没改
3. **零体积的东西会让"用大小判断状态"的代码悄悄失效**

真正省时间的是那个「环境自检」行和结构化的失败诊断 —— 把"猜"变成"看"。
