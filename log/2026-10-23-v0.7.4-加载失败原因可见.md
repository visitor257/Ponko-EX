# v0.7.4 — 让「加载模型」失败时说出原因

## 现象

装 0.7.3 之后点「加载模型」：

- 顶部三行（可用模型 / **引擎** / 存储）里**只有「引擎」那行闪一下**；
- 闪完回到「未加载 · 点下面「加载模型」」；
- 按钮还是亮的，看起来就像"点了没反应"。

0.7.2 时用户的原话是"点加载没反应"，0.7.3 之后变成"只有引擎那行闪动"。
多出来的那一下闪，是 0.7.3 加进去的两行日志和一次重画 —— 也就是说
**点击链路是通的，加载确实开始过，然后很快结束了**。

## 为什么看不出原因

三层遮蔽叠在一起：

1. **原因写错了地方。** `loadFromUi` 的 `catch` 把失败文案写进 `dlNotice`，
   而 `dlNotice` 渲染成页面**下方**的一行「提示」。用户的眼睛在顶部三行上，
   那行在他的视口之外。
2. **`engineNote` 不存在。** 「引擎」那行的取值只有 `engineUnloading` /
   `nativeReady` / `readySet` 三个来源，**没有任何一个能表达"加载出错了"**。
   所以那行的可见取值只有两种：未加载 / 已就绪。失败 = 回到未加载 = 闪一下。
3. **0.7.2 把开头的 `notifySchemaChanged()` 换成了 `notifyUiPatch`。**
   patch 只改文本、改不了 ACTION 的 `enabled`，而且下一次重画会把它覆盖回去。
   所以"正在加载…"（如果 patch 生效）只能存在到失败返回为止 —— 那正是那一闪。

## 做法

### 一、失败原因搬到用户正在看的那一行

新增 `engineNote`，非空时 `st_engine` 的取值**优先**显示它：

```kotlin
value = when {
    engineNote.isNotEmpty() -> engineNote        // 加载失败：可用内存 1.8 GB，需要 4.3 GB
    nativeReady -> "已就绪 · 48 kHz · 6 线程"
    engineLoading -> "正在加载…"
    engineUnloading -> "正在释放内存…"
    readySet != null -> "未加载 · 点下面「加载模型」"
    else -> "未加载 · 先导入或下载"
}
```

`engineNote` 的写入点在 `loadEngineBlocking` 外面包的一层 `catch`：

```kotlin
override fun loadEngineBlocking(...): EngineInfo =
    try { loadEngineInner(...) }
    catch (t: Throwable) {
        engineNote = "加载失败：${briefReason(t)}"
        logLine("加载失败：${t.message ?: t.javaClass.simpleName}")
        throw t
    }
```

原来那个函数体整体改名成 `loadEngineInner`，一行逻辑没动。**所有失败路径**
（没有模型文件 / 内存不足 / `nativeInit` 返回非 0 / 意料之外的异常）都汇总到
这一个 `catch`，不需要在每处 `throw` 前各写一遍。

`briefReason()` 取第一句、再限 40 字：`PluginException.modelInvalid` 的 message
是一整段话（"还没有可用的模型文件。到「模型」页：从本地导入两份…"），塞进一行
STATUS 会被截成半句。完整原文仍然在「运行日志」里。

### 二、加载中必须看得见

`loadFromUi` 弃用 `notifyUiPatch`，改回 `notifySchemaChanged()`：按钮要灰、
状态行要变成"正在加载…"，而 patch 改不了 `enabled`，改文本也会被下次重画覆盖。
代价是点一下多一次整页重建，但宿主 v12.1 之后重建已经不丢滚动位置了。

成功路径不再依赖"`loadEngineBlocking` 自己喊过一声"：`engineLoading` 是在
线程的 `finally` 里才翻成 `false` 的，所以那次重画必须补 —— 否则按钮停在
加载中的样子。

### 三、日志里多一行"开始加载"

```kotlin
logLine("开始加载：${chosen.origin} · ${ModelStore.human(chosen.bytes)} · $threads 线程")
```

出问题时要能区分"卡在 `nativeInit` 里"和"根本没走到这里"——这两种在界面上
都是转圈。

### 四、顺带

- `en_unload` 在调 `closeEngineBlocking()` **之前**就置 `unloadingSince`。
  那段排队窗口里按钮看起来还能点，连点两下会排进两次 `nativeFree`。
- 两个引擎按钮的 `enabled` 都加上 `!engineLoading`。

## 没做的一件事：走基类状态机

正解是调基类的 `loadEngine()` / `closeEngine()`：它们会把 `state` 推到
`LOADING` / `UNLOADED`、起前台服务、结束后回调宿主。但：

```kotlin
private val binder = object : IPonkoPlugin.Stub() {
    override fun loadEngine(models: ModelBundle?, config: EngineConfig?) { ... }
    override fun getStatus(): EngineStatus { ... }
}
```

`binder` 是 **private**，`loadEngine` / `closeEngine` / `getStatus` /
`isEngineReady` 全在里面，插件一个都拿不到。基类对子类暴露的只有
`loadEngineBlocking` / `closeEngineBlocking` 和一组 `notify*`。

所以插件自绘的「加载模型」只能直接调 `loadEngineBlocking`，`state` 停在
`UNLOADED` 不动。后果写在给宿主的报告里（同目录
`2026-10-23-报给宿主-插件拿不到引擎状态.md`）。

## 教训

**失败必须出现在用户正在看的那一行上。** 写进日志、写进页面底部的提示行，
都等于没写 —— 用户看到的是"闪了一下"，他能得出的唯一结论是"点了没反应"。

## 补丁 0.7.5：宿主发起的加载也要重画

`catch` 里补了一句 `notifySchemaChanged()`。

原因是加载**不一定是插件页发起的**：宿主功能区的「加载模型」走
`loadEngine()` → 基类 worker → 同一个 `loadEngineBlocking()`。那条路上没有
任何插件代码会重画页面，原因写进 `engineNote` 之后界面会一直停在旧状态。

用户这次看到的"闪动"很可能就是这条路：

1. 宿主把 `state` 推到 `LOADING`，功能区那行变成"正在加载"；
2. `loadEngineBlocking` 抛了，宿主把 `state` 推回 `UNLOADED`，那行变回"未加载"。

一进一出，就是那一下闪。而插件页此前对这一切完全不知情 ——
它既没有拿到 `onEngineError`，也没有任何代码在跑完之后重画。

0.7.5 之后，无论谁发起加载，失败原因都会立刻出现在「引擎」那行上。
