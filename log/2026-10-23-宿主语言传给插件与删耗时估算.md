# 宿主把界面语言传给插件，并删掉耗时估算

两件事：一件是插件侧报告的功能缺口（用户明确要的），一件是删一个算不准的东西。

---

## 一、`hostLocaleTag`：宿主把当前界面语言给插件

### 用户的原话

> 宿主获取系统语言 id，给插件，插件再通过这个 id 去判断……最后显示对应的语言

要的效果（X 中英默认中 / Y 只俄文 / Z 英俄默认英，abc 三人分别是中英俄机）：

| | A（中文） | B（英文） | C（俄文） |
|---|---|---|---|
| X（中英，默认中） | 中文 | 英文 | 中文 |
| Y（只俄文，无默认） | 俄文 | 俄文 | 俄文 |
| Z（英俄，默认英） | 英文 | 英文 | 俄文 |

**这套语义 Android 资源回落本来就是**，不需要任何新接口就能实现（见上一版 §14）。
但宿主主动把语言递过去仍然有价值，于是加了。

### 为什么不走 AIDL

加一个 AIDL 方法 `setHostLocale(String)` 要：

1. 升 `API_VERSION`
2. 重发 SDK AAR
3. **让所有插件重编**才能用

而这个值是**静态、单向、每次绑定都会重给**的 —— 正好是 Intent extra 的形状。
所以宿主在 bind Intent 里带一个 key：

```kotlin
const val EXTRA_HOST_LOCALE = "com.litertchat.ponko.extra.HOST_LOCALE"
```

- 老插件不读这个 key → **行为完全不变**（这是重点）
- 新插件读它 → 拿到语言

**AIDL 一个字节都没改，`API_VERSION` 仍是 12。**

### 宿主给的是什么

`context.resources.configuration.locales[0].toLanguageTag()`

不是 `Locale.getDefault()`：

- `getDefault()` 是**进程级**的，Android 13+ 给单 App 设过语言时会和实际不一致
- `configuration.locales[0]` 才是**这个 App 正在用的**，也就是用户眼睛看到的那个

也不是拼 `language + "-" + country`：标签可能是 `zh-Hans-CN`、`sr-Latn`，
拼字符串会把文字系统那一段截坏。用 `toLanguageTag()` 生成、插件用
`Locale.forLanguageTag()` 解。

### 插件侧拿到什么

```kotlin
protected val hostLocaleTag: String        // "zh-CN" / "en" / "ru" …
protected fun localizedContext(): Context  // 按它覆盖 configuration 的 Context
```

`localizedContext()` 里做了 `cfg.setLocale(loc)` + `cfg.setLocales(LocaleList(loc))`，
所以 `getString()` 走的是"按宿主语言解析 + 正常多级回落"。

**没传时返回系统默认语言，不是空串** —— 否则老宿主上插件会突然白屏。

### 文档里必须强调的一件事

**优先用资源限定符，`hostLocaleTag` 只兜三类资源解决不了的情况**：
译文在 assets/JSON 里、per-app language 导致系统与宿主不一致、需要按语言改行为。

否则读者会以为"要支持多语言就得写 if-else 挑字符串"，那是个倒退。

## 二、删掉耗时估算

### 删的是什么

参数区「文本」下面那行：`约 24.1 秒语音 · 按当前插件速度估算需 4.0 分钟 ~ 12.1 分钟`。

### 为什么删

用户直接说不需要。但我认同这个判断，理由是它**算不准而且不可能算准**：

```kotlin
val sec = (s.length / 4.5).coerceAtLeast(0.5)   // 中文 4.5 字/秒
val lo = sec * 10                                // RTF 10
val hi = sec * 30                                // RTF 30
```

真实速度取决于插件实现、机型、CPU/GPU 后端、线程数 —— 三个硬编码系数想覆盖这些，
偏差几倍很常见。而**给用户一个偏差几倍的倒计时比不给更糟**：他会按那个数字判断
要不要继续等，等超了就以为卡死了，然后去杀进程。

而且这条**跨语言还有个隐藏错误**：`4.5 字/秒` 是中文假设。英文按字符算，
同一个系数会让英文文本的预估明显偏长 —— 上一轮 i18n 我翻译了它的文案，
但没发现系数本身是中文专属的。这是那轮的遗漏，现在整条删掉了。

真需要进度，应该由插件报（`onSpeakStage` 已经能报阶段，精确到秒就该在协议里带
progress），而不是宿主猜。

### 连带删掉的

- `fmtDur()`（秒 → "45 秒"/"2.3 分钟"/"1 小时 5 分"），只服务于这个估算
- 死资源 `s_551`、`s_590`、`s_611`、`s_612`、`s_623`、`s_624`（中英各 6 条）

删死资源是为了不让下一个人以为还有地方在显示时长。

## 一句话版

- 静态、单向、每次连接都重给的信息 → **Intent extra，不要 AIDL**（不动接口、不重编插件）
- 给插件传语言要取 `configuration.locales[0]`，不是 `Locale.getDefault()`（per-app language 会不一致）
- 语言标签用 `toLanguageTag()`，**不要拼** `language + "-" + country`（`zh-Hans-CN` 会被截坏）
- 新加的出口在文档里要写"**优先用资源**"，否则会被当成"必须手写 if-else"
- **算不准的估算比没有更糟**：用户会拿它做判断，误差几倍就变成"看起来卡死了"
- 删功能要连死资源一起删，否则后人以为还在用
