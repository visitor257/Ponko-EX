# 2026-10-22 · 插件引擎生命周期与「试听」语义（宿主侧四条反馈）

来源：Ponko-EX_VoxCPM2 线真机实测，四条里**三条是我的 bug**。

真实价值在于：这三条在 Echo 上全都测不出来 —— 不是运气，是 Echo 太轻。
Echo 的 `loadEngineBlocking` 只是 `sleep(800)`，`closeEngineBlocking` 什么都不做，
所以"卸载慢"、"卸载没回调"、"卸载窗口内合成"这三件事**根本不会发生**。

> **教训先行**：用一个玩具插件当唯一验证目标，会系统性漏掉"重"的那种失败。
> 轻插件能验证链路通不通，验证不了时序和资源的边界。

---

## 1（高）卸载后按钮不复位，再点反而把模型加载回来

### 现象
点「卸载引擎」→ 提示"正在卸载中…"→ 按钮文字仍是「卸载引擎」→ 然后不动了。
再点一次 → **3.5 GB 又灌回去**。

### 原因
我写的是「延迟 250ms 查一次状态」：

```kotlin
act.window.decorView.postDelayed({
    val still = session.engineReady(pkg)
    ...
    refreshEngineLabel(pkg)
}, 250)
```

这个"一次"极可能落空：

| 情况 | 实际耗时 |
|---|---|
| 空闲，但模型几 GB，free 本身慢 | 几百毫秒 |
| 正在推理，要等插件查 cancelFlag 再逐块退出 | 几秒 |
| 插件进程被系统冻结过 | 不确定 |

落空之后**没有任何时机再刷新按钮**（只有这里和 `onEngineReady` 会调
`refreshEngineLabel`）。于是界面停在"仍是卸载引擎"，而实际早卸完了。

用户再点一次：`engineReady()` 此刻是 `false` → 走 else 分支 → `loadEngine`。
**"卸载不掉，反而又加载了"** 就是这么来的。

### 根本问题：AIDL 里没有"卸载完成"的回调
`IPonkoCallback` 有 `onEngineLoaded` / `onEngineError`，**没有 `onEngineUnloaded`**。
加载的两条路都有回调，卸载一条都没有 —— 宿主只能猜时间。

### 做法
`IPonkoPlugin` 里其实早就有能用的东西，只是宿主**从来没调过**：

```kotlin
// IPonkoPlugin.aidl
EngineStatus getStatus();   // 同步、O(1)
```

`grep getStatus() app/src/main/java/.../plugin/` 之前零命中。

改成**轮询到状态真的变**：

```kotlin
private fun awaitEngineUnloaded(pkg: String) {
    val deadline = SystemClock.elapsedRealtime() + 5_000
    val probe = object : Runnable {
        override fun run() {
            if (openUiPkg != pkg) return          // 页面切走了就别再刷
            val st = session.engineState(pkg)
            val done = st == EngineState.UNLOADED
            if (!done && elapsed < deadline) {
                decorView.postDelayed(this, 200)
                return
            }
            setActionEnabled("engine", !speaking)
            refreshEngineLabel(pkg)
            setUiHint(if (done) "引擎已卸载，内存已释放" else "引擎释放超时（5 秒）…")
        }
    }
    decorView.postDelayed(probe, 200)
}
```

顺带两个好处：

- 卸载期间按钮**先禁用**，用户点不出"卸载 → 加载"
- 超时不再说"仍在卸载中"（那是个死状态），改成"可以再点一次或停用插件"——
  给出下一步比陈述现状有用

### 没做的
根治方案是加 `onEngineUnloaded` 回调。但那要动 AIDL → 重发 AAR → **所有插件重编**。
轮询 20 行就能解决，先不做。等下次 breaking change 一起。

## 2（中）「试听」每点一次就重新推理，没法重播

### 现象
合成完自动播放。想再听一遍 → 只能再点「试听」→ 重跑推理，手机上 1~2 分钟。

### 原因
不是 bug，是**缺一个动作**。宿主其实已经留着上一次的文件：

```kotlin
private var lastAudioFile: java.io.File? = null   // 存在
currentUiPage?.setActionEnabled("save", true)     // 但只用来给「保存」判可点
```

播放逻辑内嵌在 `playResult()` 里，想加"重放"只能复制一遍，所以一直没加。

### 做法
1. 把播放那段抽成 `playFile(f: File)` —— 让"重放"和"合成后自动播"用同一份代码
2. 加一个「播放」动作，`enabled` 和「保存」同一个条件（有产物才亮）
3. **有产物后把「试听」改名「重新合成」**

第 3 点单独说：不改名的话，用户点「试听」以为只是重放，白等一分钟后才发现不是。
名字要跟着语义走 —— 同一个按钮在不同状态下含义不同，那就该换名字。

现在按钮是：`加载/卸载引擎 · 重新合成 · 播放 · 停止 · 保存`，
一眼能分清"再推理一次"和"再放一遍"。

## 3（低）卸载窗口内点试听，报"上一段语音还在生成"

### 现象
点「卸载引擎」后马上点「试听」→ 提示"上一段语音还在生成，请稍候"。
实际什么都没在生成。

### 原因（这条是我自己引入的）
SDK 的 `closeEngine` 借用了 `busy` 这个"有任务在跑"的标志：

```kotlin
override fun closeEngine() {
    if (!busy.compareAndSet(false, true)) { cancelFlag = true }
    //  ↑ 空闲时 CAS **会成功**，busy 变成 true
    worker.execute { ... }   // busy 要等 worker 的 finally 才复位
}
```

于是这段窗口里 `synthesize` 命中：

```kotlin
if (!busy.compareAndSet(false, true)) {
    postError(BUSY, "上一段语音还在生成，请稍候")
}
```

**`busy` 被当成了两个意思**：「有合成在跑」和「引擎正在关」。这两件事对调用方
的含义完全不同。

### 做法
加独立的 `@Volatile closing` 标志，`synthesize` 在 `closing` 时回 **`NOT_READY`**：

```kotlin
if (closing) {
    postError(PluginException.notReady(), req.requestId)
    return
}
```

为什么 `NOT_READY` 是对的：宿主对 `NOT_READY` 有现成处理 ——
自动重载引擎 + **补发这次试听**。语义正好（引擎确实不在），
而 `BUSY` 只会把"上一段还在生成"这句谎话显示给用户。

**成本**：改 SDK → 重发 AAR → 插件重编。这条值得做，因为文案误导很难查 ——
用户会去翻"我哪段语音还在生成"。

## 4（低）文档说 intro 支持 markdown 粗体，实际不解析

### 现象
`plugin-guide.md` 第 9 节的示例里写着：

```kotlin
intro = "这段说明会显示在页面顶部，可以用 **粗体**、`代码` 这类行内格式。"
```

而宿主的 `hintText()` 就是 `text = t`。照着写的插件在界面上看到一堆星号。
VoxCPM2 线踩过，v0.2.0 只好把文案全改成「」和换行。

### 做法：兑现承诺，而不是删掉承诺
两个选择（删文档 / 实现），我选了实现 —— 因为它不是无用功能：
intro 是一段解释文字，粗体能显著提高可读性。

但**只实现两种**：`**粗体**`、`` `等宽` ``。标题、列表、链接、表格一律按原文。
理由：

1. 每多解析一个语法，就多一处"插件以为是这样、界面是那样"的错位
2. 文本里可能合法地出现星号（MIME 里的通配符），语法越多越容易误伤

实现上有个细节：**不能"先加 span 再删标记"**。删字符会让后面所有下标失效，
`**` 是两字符、`` ` `` 是一字符，删完长度都不一样；`setSpan` 之后再 `delete`
还会让 Span 自动移位，容易差一两个字符（表现是粗体范围偏了）。

改成单遍扫描：边扫边往新串 append，顺手记下每段起止，扫完统一 `setSpan`。
下标从头到尾只有"新串里的位置"一种含义。

## 5. 踩坑：Kotlin 块注释支持嵌套，注释里写 `/` + `*` 会炸

### 现象
编译报 181 个 `Unresolved reference`（`dp`、`wrapWrap`、`smallHint`… 全是类成员），
外加：

```
Syntax error: Missing '}'
Syntax error: Unclosed comment   (指向文件末尾第 1042 行)
```

看起来像类结构被写坏了，实际结构完全正常。

### 原因
我在写第 4 条那段注释时，举了个例子说"文本里可能合法地出现星号（比如文件类型
`audio/*`）"。

**`audio/*` 里的 `/*` 又开了一层块注释** —— Kotlin 的块注释是**可嵌套**的
（和 C/Java 不同，那里 `/*` 在注释里没有意义）。

于是注释多了一层没闭合，`*/` 只关掉了内层，外层一直吃到文件末尾，
**把后面所有成员定义都变成了注释内容**。

所以那 181 个"未解析引用"不是类坏了，是那些方法**已经被注释掉了**。

### 做法
把 `audio/*` 改写成"文件类型 MIME 里那个通配符"，不出现 `/*` 字面组合。
并在那段注释里留了一句提醒，防止下次再踩。

### 教训
`Unclosed comment` 指向文件末尾时，**根因几乎总在文件中间的某个块注释里**。
去找注释正文里的 `/*`，而不是去数括号。

反直觉的地方：**写一条关于星号的注释，反而因为星号把代码注释掉了。**

## 6. 顺带：为什么这三条 Echo 测不出来

值得单独记，因为它决定了以后的验证策略。

| 问题 | 为什么 Echo 测不出来 |
|---|---|
| 卸载慢/无回调 | Echo 的 `closeEngineBlocking` 是空的，瞬间完成 |
| 没法重播 | 能测出来（任何插件都有这个问题），但 Echo 合成只要几秒，用户不会在意 |
| 卸载窗口内合成 | 窗口宽度 ≈ 0，没有机会落进去 |

**结论：轻插件验证"链路通不通"，重插件验证"时序和资源"。两者不能互相替代。**

以后改宿主侧的引擎生命周期，必须拿一个加载/卸载都慢的插件验一遍。Echo 只能当冒烟测试。
